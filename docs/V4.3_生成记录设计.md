# H3 Studio V4.3：生成记录持久化设计与实施状态

> 实施状态（2026-11-10）：V4.3 已实现本设计的核心能力。依据实际服务器验收，`/data/minimax-h3/outputs` 位于宿主机持久化目录，故改用**原地索引，不复制 MP4**。SQLite 文件位于 `/data/minimax-h3/history/history.sqlite3`。WebUI 新生成任务记录完整参数；旧视频及同目录的 API 文件通过扫描导入，来源和参数不做推断。以下为原始设计背景，其中关于复制/迁移 MP4 的建议已由原地索引替代。

## 目标与基线

本文件基于 V4.2 压缩包实际代码、SGLang `v0.5.22` 源码（`minimax_h3.py`、`save_outputs`、`VIDEO_STORE`）制定。V4.2 仍然只有一个 `gr.Video` 输出；浏览器主题使用 localStorage，但没有历史记录存储。

目标是跨浏览器刷新、容器重启后，能够列出、播放、下载已完成的所有保留视频，并可查看提示词、生成时间、参数、状态。应区分 WebUI 内产生的任务和 `/v1/videos` API 内产生的任务。

## 发现

1. WebUI `generate()` → `_generate_minimax_h3()` → `save_outputs()` → `output_paths[0]`，Gradio 仅接收本次视频路径；当前回调没有注册索引。
2. `SamplingParams.output_path` 如缺省会参考 `server_args.output_path`，若服务器未提供则可能禁用保存；需要在服务端核实实情。
3. HTTP API 的 `GET /v1/videos` 使用 `VIDEO_STORE = AsyncDictStore()`，其存储是**内存字典**，不会可靠地跨进程/容器重启保存，也不能直接覆盖所有 WebUI 视频。
4. 已创建的 MP4 是否存在于持久宿主挂载路径，尚需核验实际 `docker inspect` 和服务参数；仅靠本仓库无法证明旧视频已保留。

## 推荐架构

- **磁盘**：宿主目录建议 `/data/minimax-h3/history`，挂载至容器 `/data/minimax-h3/history`，目录下 `videos/` 存 MP4，`history.sqlite3` 存记录。不修改权重目录。
- **写入**：WebUI 生成成功后，先把 `save_outputs()` 返回的 MP4 复制或原子移动到 `videos/<uuid>.mp4`；验证文件存在且非空后，使用 SQLite 事务写入一条记录（`completed`）。不得仅保存 Gradio 临时文件 URL。
- **任务状态**：提交开始时分配 UUID 记录 `running`，成功写 `completed`，失败写 `failed` 和简短错误。容器重启后对未完成记录恢复为 `interrupted`（无任务恢复功能不应伪造成功）。
- **模型调用**：仅包装 WebUI 已有 `generate`，不改 `build_minimax_h3_sampling_params_kwargs` / 调度器内部逻辑，不通过浏览器 JS 猜测是否完成。
- **展示**：在现有 Gradio 页面新增“生成记录”选项卡，`gr.Dataframe` 或 `gr.Gallery` 分页展示，选择记录后由 `gr.Video` 播放，`gr.DownloadButton` 下载。加刷新和筛选；表单显示创建时间、提示词、seed、步数、时长、状态。
- **存量**：可提供一次性扫描历史输出目录的导入命令，**只导入实际存在的媒体文件**；没有元数据的旧文件标记为“导入记录”，不能凭空补出提示词和任务时间。
- **安全**：文件读取必须限制在持久目录中，使用 UUID 索引查数据库，不接受前端直接传任意绝对路径；如对外开放 18080，必须考虑鉴权或限制内网访问。
- **并发**：SQLite WAL + 短事务，不要在持锁事务内执行推理或 FFmpeg 编码。多输出应每段单独记录（现有 UI `output_paths[0]` 仅返回第一段）。

## 分阶段验收

1. 配置可写、重建后仍可访问的宿主挂载目录；磁盘空间和容量规划通过。
2. 成功生成一条 MP4，列表出现且可播放、下载，下载字节与磁盘原文件一致。
3. 页面刷新、多浏览器访问后，记录仍在；重建容器后保留。
4. 同时提交多任务，UUID 不冲突；失败任务保留失败状态且不出现错误视频链接。
5. 目录断开、磁盘空间不足、文件缺失和恶意路径输入能安全处理。
6. 如需把 **API 生成**的视频也纳入同一列表，需添加 API 完成后登记/定期导入逻辑；不能只改 WebUI 来承诺覆盖 API 全部历史。

## 开始实现前需向实际服务器核实

```bash
docker inspect sglang-h3 --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
docker exec sglang-h3 sh -lc 'df -h /data/minimax-h3 /tmp; ls -lah /data/minimax-h3/logs 2>/dev/null | head'
grep -n -E 'output-path|output_path|volumes:|/data/minimax-h3' /data/minimax-h3/deploy/compose.yaml
```

以上三个命令只读，不会停服务。不能仅凭 ZIP 确认旧视频文件是否仍然存在。
